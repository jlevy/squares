## Overview

On 2026-10-11 the owner asked for project documentation to live in a structured place
under `docs/`, organized by one consistent set of rules, with all-caps names reserved
for the few cases where they make sense.
This plan surveys where the repository’s 2,075 tracked Markdown files sit today, names
the inconsistencies, lists what any move has to respect, and proposes one taxonomy, one
naming rule and a migration in eight slices.

Today seven project documents sit at the root beside the three entry points, twelve sit
loose in `docs/project/`, four project-wide runbooks live inside `packing/campaign/`,
two generated views sit away from the registers they render, and sixteen Markdown names
use capitals without a convention behind them.
The proposal leaves the root with `README.md`, `AGENTS.md`, `CLAUDE.md` and `LICENSE`;
puts every authored project-level document in a kind directory under `docs/project/`;
and keeps component guides, schema-governed records and generated views beside the code
or data they describe.

## Goals

- One placement rule that decides where any new document goes from the kind of document
  it is.
- A root that holds entry points and tool-mandated files only.
- No loose Markdown in `docs/project/`: every document in a directory named for its
  kind.
- Lowercase kebab-case names, dated names for records, undated names for maintained
  documents, and a short, closed list of all-caps exceptions.
- A migration in which every commit passes the gate, every link keeps resolving, and the
  moves that need tool changes are known before they start.
- The layout held by a check rather than by care, so it does not drift back.

## Non-Goals

- Moving schema-governed records (frontier cases, hypotheses, experiments, sessions,
  agendas, explorations) or the run reports and reviews that sit beside their data in
  `packing/`. The document map matches 1,153 of them through collections whose schema
  contracts name those paths.
- Renaming record identifiers (`H-`, `X-`, `VE-`, `X048-`); see owner decision 6.
- Moving plans between tbd’s spec lifecycle directories (`specs/active/` to
  `specs/done/`). That is the job of `tbd shortcut update-specs-status`, in a separate
  pass.
- Tool configuration at the root (`Makefile`, `package.json`, seven `tsconfig*.json`
  files, `biome.json` and the rest).
  It is not documentation; a separate survey can decide whether it should consolidate.
- Content edits beyond what a move requires: link rewrites, path constants, and the
  layout descriptions in `README.md`, `AGENTS.md` and `conventions.md`.

Five kinds of reference never fail, and the migration has to find them by search:

1. Stale literals in `validate.py` `touches`, which switch a step off for the moved
   file.
2. Links in `AGENTS.md`, `CLAUDE.md` and the dot-directories, which the link checker
   does not read. `.github/ISSUE_TEMPLATE/result-registration.md` links the result-import
   runbook this way.
3. Absolute `github.com/jlevy/squares/blob/main/<path>` links in Markdown, which the
   checker skips as external.
4. Bare filename mentions in prose, docstrings and register prose.
   They stay accurate when a move keeps the basename and go stale when a rename changes
   it.
5. Retained non-Markdown artifacts (logs, receipts, `jsonl`, resource-usage YAML,
   checkpoint text) that name old paths.
   They record what was true when they were produced, and stay as they are.

Outside the repository, three things matter.
GitHub does not redirect a moved file, so a `blob/main` link to a moved document from an
issue, a PR body, a reply to an author, another repository or a search engine stops
resolving. The site’s addresses for the reader documents (`tutorial.html`,
`synopsis.html`, `conventions.html`, `epistemics.html`, `development.html`,
`readme.html`) are fixed by name and do not depend on source paths.
The papers pin every repository citation to the commit they were built from, so moves do
not break them.

Two repository conventions bear on every move.
`AGENTS.md` requires every declared path in the record to be repository-relative, which
still holds; the mover rewrites those strings exactly.
`conventions.md` section 2 says to use `repren` for renames and that a published paper’s
address keeps working after a move.
The precedent is the 2026-08-28 hoist (PR #59): 1,159 renames with `repren --renames` in
a renames-only commit, then repairs to configuration and path constants (45 files),
links, the map and generated views (70 files), and declared record paths (9 files).
The regularization policy’s interim move touched 8 files.

## Design

### Placement Rules

Three rules, applied in order:

1. **Beside code or data**, if the document describes one directory’s contents (a
   component README or guide), is a schema-governed record, reports on one run’s data,
   or is generated from a register.
   It moves when that directory moves.
   A generated view sits beside the register it renders.
2. **At the root**, if a convention or tool requires it there: `README.md`, `AGENTS.md`,
   `CLAUDE.md`, `LICENSE`.
3. **Under `docs/project/<kind>/`** otherwise: every authored document about the project
   as a whole.

Inside `docs/project/`, two questions pick the directory.
Is the document a dated record or a maintained document?
If maintained, does it explain what is, state what must be, or say what to do?

### Directory Taxonomy

```
docs/
├── project/
│   ├── README.md            Index of this tree (decision 9)
│   ├── document-map.yaml    Role, authority and lifecycle of every durable document
│   ├── document-map.schema.yaml
│   ├── guides/              Maintained explanations
│   ├── policies/            Maintained rules
│   ├── runbooks/            Maintained procedures
│   ├── specs/active/        Plans and spikes (tbd)
│   ├── research/            Dated topical syntheses
│   ├── reviews/             Dated reviews
│   ├── postmortems/         Dated failure analyses
│   └── handoffs/            Dated handoffs
└── tbd/                     Managed by `tbd docs fork`
```

| Directory | Holds | Name form | Lifecycle | Files today, then |
| --- | --- | --- | --- | --- |
| `guides/` | What the project is, where it stands, how to build and verify it | `topic.md` | maintained | 0, then 5 |
| `policies/` | Rules a contributor must follow | `topic.md` | maintained | 1, then 4 |
| `runbooks/` | Step-by-step procedures, one per workflow or process | `topic.md` | maintained | 0, then 4 |
| `specs/active/` | Plans and spikes | `plan-YYYY-MM-DD-topic.md`, `spike-YYYY-MM-DD-topic.md` | transient | 55, then 56 with this plan |
| `research/` | Topical syntheses | `research-YYYY-MM-DD-topic.md` | retained | 41, then 42 |
| `reviews/` | Reviews of the project’s work | `review-YYYY-MM-DD-topic.md` | retained | 292, then 293 |
| `postmortems/` | Failure analyses | `postmortem-YYYY-MM-DD-topic.md` | retained | 2 |
| `handoffs/` | Session handoffs | `handoff-YYYY-MM-DD-topic.md` | retained or superseded | 0, then 7 |

The prefix stays `docs/project/` rather than `docs/` for three reasons.
tbd’s shortcuts write plans, research briefs and reviews to `docs/project/` paths;
`tbd docs fork` owns `docs/tbd/`, so one prefix separates authored documents from
tool-managed ones; and 57 code, test, template, workflow and registry files already name
`docs/project/{specs/active,research,reviews}/` paths (421 occurrences), none of which
need to change. For the same reason `specs/` keeps its name: a `plans/` directory would
read more plainly, but tbd’s planning shortcuts and `update-specs-status` read
`docs/project/specs/{active,done,future}/`.

### Naming Convention

1. **Lowercase kebab-case** for every authored file and directory:
   `[a-z0-9]+(-[a-z0-9]+)*`, then the extension.
   A version token keeps its dots
   (`review-2026-10-04-n11-optimality-paper-v0.1.4-changes.md`).
2. **Dated records** are `<type>-YYYY-MM-DD-<topic>.md`, where `<type>` is the singular
   of the directory: `plan` or `spike`, `research`, `review`, `postmortem`, `handoff`.
   The date is the record’s own and does not change when the file moves.
3. **Maintained documents** are undated `<topic>.md`. The kind word is added only when
   the topic alone would mislead: `regularization-policy.md`, because regularization is
   also an algorithm, but `conventions.md` and `epistemics.md`.
4. **Registered identifiers keep their registered spelling** in filenames (`H-001-…`,
   `X-001-…`), as `conventions.md` section 2 checks.
5. **Capitals appear only in** `README.md` (and `README.txt` in retained bundles),
   `AGENTS.md`, `CLAUDE.md`, `SKILL.md`, `LICENSE` and a third-party asset’s
   `LICENSE.txt`, GitHub’s `PULL_REQUEST_TEMPLATE.md` and `ISSUE_TEMPLATE/`, and
   identifiers under rule 4.
6. **A generated view keeps its name, lowercased**, beside its register
   (`packing/frontier/results.md` beside `results.yaml`).

## Implementation Plan

Slices run in order.
Each one is a single commit that passes the gate: the mover renames and rewrites in the
same commit, and Git’s rename detection keeps `git log --follow`, as it did for the
hoist. The moves cannot run as parallel lanes, since every slice edits the same index
files (the document map, `math-markup.yaml`, the synopsis’s generated table and
`README.md`); slice 0’s four tools are disjoint and can.

### Slice 0: Tools Before Moves

- [x] `devtools.move_documents`, with
  [jlevy/squares#579](https://github.com/jlevy/squares/pull/579): it takes old-to-new
  pairs and validates the whole list before writing anything (every path inside the
  repository, distinct new targets, no target that is another move’s source or sits
  under a file). `--apply` runs every `git mv`, then writes each rewrite at its new
  place, and undoes all of it if any step fails.
  It rewrites every relative Markdown link that resolves to an old path and every
  outbound link of a moved file, and every exact repository-relative string in any
  tracked text file, so code, tests, configuration, workflows, registers, the map,
  `.flowmarkignore`, `.gitattributes` and `prose-ceremony.yaml` all follow.
  A file is text when it decodes as UTF-8 with no NUL byte, whatever its name.
  It keeps `math-markup.yaml` sorted and line endings byte for byte, and leaves fenced
  code, footnotes, symbolic links, files whose blob a tool pins, and retained artifacts
  (the archive, the reconciliation records, `*.jsonl` receipts, patches) alone.
  It reports a moved path left in fenced code and a file that names one but is not text.
  A dry run prints each file’s count; 34 moves take about five seconds.
- [ ] The rest of the mover (think-qgq1): two steps for a case-only rename, which the
  target-exists check refuses on a case-insensitive filesystem today; and a report of

  links it leaves, and the references it rewrites in `AGENTS.md`, `CLAUDE.md` and
  dot-directories.
- [ ] `devtools.check_document_names` in the records tier: capitals only under naming

## Testing Strategy

- The mover’s tests run on temporary repositories: inbound links from several depths,
  with and without anchors; reference-style links; outbound links of a moved file; links
  inside fenced code left alone; exact register strings rewritten; retained artifacts
  untouched; case-only renames.
- After each slice: `packing-validate --records`, since register paths change, and
  `packing-validate --fast`, the pull-request tier.
  That covers the link checker, the map, `check_readme`, `check_synopsis`,
  `validate_schemas`, the math ratchet, `check_generated_markdown`, the ceremony check,
  `test_pages_scope` and the naming check.
- Slices 2, 3 and 5 change site sources, so they also run the full `packing-validate`
  and a local site preview before merging.
- After each slice, `git grep -F` for every old path over live code, configuration,
  registers, `AGENTS.md`, `CLAUDE.md` and the dot-directories returns only retained
  artifacts.

## Rollout

Slices 0 and 1 land first and prove the mover on low-stakes files.
Slices 2 and 4 follow, then slice 3, slice 5 in a quiet window, then 6 and 7. Each slice
is its own pull request, stacked where they depend on each other (`github-stacked-prs`
is granted), and each leads with what it cost.
After slices 2, 3 and 5 merge, the Pages deploy regenerates the site’s GitHub links;
page addresses do not change.
If decision 4 adds one, the docs index lists former paths for readers who arrive from an
old `blob/main` link.

## Owner Decisions

Each has a recommended default; “as recommended” approves all ten.

1. **Scope.** Authored project-level documents move under `docs/project/`; records,
   component guides and generated views stay beside their code or data.
   *Recommended.*
2. **Prefix.** One prefix, `docs/project/<kind>/`, aligned with tbd.
   *Recommended*, over putting the reader documents at `docs/` and the rest under
   `docs/project/`.
3. **Generated views beside their register**: `defects.md` to `packing/defects.md`,
   `site-urls.md` to `packing/site-urls.md`. *Recommended*, over a
   `docs/project/reference/` directory, which would break the rule 18 of 20 views
   follow.
4. **The synopsis and tutorial leave the root.** External `blob/main` links to the seven
   moved root documents stop resolving, since GitHub does not redirect moved files; site
   addresses stay. *Recommended*: accept, and list former paths in the docs index.
   Leaving stub files at the old paths would keep the root cluttered.
5. **Lowercase the five generated frontier views.** *Recommended*, in a window with no
   open result-registration pull request.
6. **Identifier prefixes.** Keep `H-`, `X-`, `VE-` and `X048-` as registered.
   *Recommended*, over renaming 360 files referenced from about a thousand.
7. **Retained records with capitals** (two `NOTES.md`, `D1_REPORT.md`, `D2_REPORT.md`):
   rename them (11 links).
   *Recommended*, over leaving them as produced.
8. **The four workflow runbooks move to `docs/project/runbooks/`.** *Recommended*, over
   leaving them with the campaign.
9. **The generated document-map table moves from the synopsis to a generated
   `docs/project/README.md`.** *Recommended*, over keeping it in the synopsis and
   writing a short hand-maintained index.
10. **The schema gains `policy` and `guide` roles.** *Recommended.*
