The pull-request `validate` job's checks tier has a 195 s ceiling, and since `main` (the n = 11 stack, #157 to #172) merged into the workbench stack it runs at the ceiling:

| run | head | checks tier | largest steps | outcome |
| --- | --- | ---: | --- | --- |
| 34912025099 | #125 `79cac315` | 205.8 s | exact verification 126.4 s, type floor 114.8 s | failed; passed on rerun |
| 34912572369 | #160 `72629c03` | 200.7 s | exact verification 121.2 s, type floor 100.4 s | failed; rerun pending |

A gate that passes or fails on runner variance certifies nothing either way. Per `OR-13` and `OR-14`, the fix is measured, not a bigger number:
- clock the tier at its declared reference shape (`packing/devtools/gate-budgets.yaml`, `checks` entry) on the merged tree;
- find which of main's new steps pushed `exact verification` from its recorded ~62-80 s to ~121-126 s;
- either move an unavoidably slow step off the pull-request surface with its own measurement, split the tier onto another runner as `geometry` was, or speed up the step;
- record the new reading in the budget file.

This is stack-wide infrastructure, so it belongs to the lowest PR (#125) or to main directly.

## Notes

**2026-09-14, readings from `main`'s own pull requests.** The ceiling is not the stack's doing alone:

| run | branch | checks tier |
| --- | --- | ---: |
| 34906462182 | #172 `codex/synopsis-research-rollup` | 143.05 s (73%) |
| 34907502102 | #172 `codex/synopsis-research-rollup` | 184.47 s (95%) |
| 34912572369 attempt 2 | #160 `72629c03` | 199.74 s (102%): exact verification 118.5 s, type floor 112.7 s, soundness perimeter 73.0 s |

#160 has now failed twice in a row (200.7 s, 199.7 s). One branch reading from 143 s to 184 s means runner variance alone spans a quarter of the ceiling, so the fix is to take a measured step off this tier, or split the tier, not to rerun until it passes.

**2026-09-14, the cause, and main already has the fix.** Per-step CI times from the validation-timing artifacts:

| step | #172 run a | #172 run b | #160 attempt 1 | #160 attempt 2 |
| --- | ---: | ---: | ---: | ---: |
| exact verification | 86.0 | 116.6 | 121.2 | 118.5 |
| type floor (basedpyright) | 67.7 | 82.9 | 100.4 | 112.7 |
| soundness perimeter | 52.5 | 69.5 | 77.2 | 73.0 |
| the branch cost rollup renders | 44.9 | 58.3 | 60.9 | 60.6 |
| bead tree | 12.0 | 15.8 | 16.6 | 18.7 |

- **Runner variance.** Between #172's two runs every step scales by about 1.3x together. That is the runner's speed, not a regression in any one step.
- **The rollup check.** The code calls it "sub-second", yet it took 45 to 61 s on CI and 84 s locally. A local profile shows `render` running once per branch (52 times), each call re-parsing every resource receipt: 33,459 YAML loads, 107 of 111 profiled seconds. `main` #174 already fixed this in `65a5c001` ("perf: parse PR rollup corpus once", VE-005), so merging `main` into the stack removes about a minute of step time from the checks tier.
- **What the stack itself adds** is type-floor time: 83 s on #172's slower run against 100 to 113 s on #160, from the Python #160 adds under `packages/workbench/tools`.

**Next:** merge `main` (#174, #176) into the stack after the review lanes finish. Then re-read `--checks` on #160. If it still sits within 10 s of 195 s, price the type floor's #160 growth as a separate measurement.
