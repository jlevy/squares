`packing-validate --push` at its default `--jobs` cannot finish a broad selection inside its
own 1800s cap, and the reason is arithmetic rather than a defect.

Measured on 2026-09-10, 4 cpus:

| `--jobs` | pytest workers | distribution |
| --- | --- | --- |
| 1 | 4 | `-n 4` |
| 2 | 3 | `-n 3` |
| 4 | 1 | none, serial |

`_pytest_workers(jobs) = max(1, cpus - jobs + 1)` is right for the gate, where `jobs` outer
slots really are busy. Run standalone they are not, so the default leaves pytest one process.
A run of the tier with `select_tests` returning `everything` then took `1801.00s` on
`reachable behavioral tests` and was killed at the 1800s ceiling, against `184.22s` for the
same suite on the runner at its own parallelism (4834 passed). Nothing was wrong with the
code: the invocation was misconfigured for its own selection.

`development.md` already names the remedy -- `packing-validate --push --jobs 1` for a broad
diff -- which is evidence the edge is known and also that documentation is not closing it: this
run was made by the same person who wrote that paragraph.

Worth considering, cheapest first:

1. When the selection is `everything`, say so before the step runs and name the remedy in the
   same line, so the 30 minutes are not spent before the advice is read.
2. Better: let the tier choose its own workers when it is the only thing running. The gate
   passes `--jobs` because it knows how many outer slots it has busy; a standalone invocation
   knows the opposite. A flag the gate sets, rather than a default every human has to
   remember, puts the knowledge where it already exists.

Either way the cap stays: a step that needs more than 1800s serially is a step that should be
parallel, which is D-488's lesson and not to be relitigated by raising the ceiling.
