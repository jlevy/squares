`.github/workflows/packing-validation.yml` has four `working-directory:
explorations/packing` settings: two `defaults.run` blocks (the `validate` and
`macos-portability` jobs) and two `setup-uv` step inputs. All four become `packing`.

`cache-dependency-glob: uv.lock` is resolved relative to the working directory and needs
no change once that is right. Note defect D-? in `defects.yaml:5840` records the failure
mode when these two disagree: both jobs repeated the directory in the glob, the lookup
targeted `explorations/packing/explorations/packing/uv.lock`, and the cache silently
matched nothing. Verify the cache actually hits after the change rather than assuming.

The `push:` `paths:` filter lists `explorations/packing/**`. With the project at
`packing/` plus a docs tier at the root, a path filter no longer usefully narrows
anything; drop it and let pushes to main run the gate. Leave `pull_request: {}`
unfiltered as it is now, for the reason the existing comment gives: a filtered required
check hangs pending forever when no path matches.

`packing/tests/test_module_boundaries.py:207` asserts
`setup_options["working-directory"] == "explorations/packing"`. It must change in the
same commit or CI fails on its own guard.
