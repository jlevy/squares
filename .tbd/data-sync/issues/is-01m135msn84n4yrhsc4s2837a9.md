packing.verified_upper_bound carries value and exact_form for all 100 cases, and the naming invites reading it as 'the verified exact value of s(n)'. It is not. It is a bound this repository can independently certify, and for 33 of the 100 it is WEAKER than the best known construction recorded two fields above it:

  n=82  reported 9.535534  verified 10       gap +0.4645  exact_form: 10
  n=65  reported 8.535534  verified 9        gap +0.4645  exact_form: 9
  n=50  reported 7.571429  verified 8        gap +0.4286  exact_form: 8
  n=37  reported 6.598620  verified 7        gap +0.4014  exact_form: 7
  n=26  reported 5.621320  verified 6        gap +0.3787  exact_form: 6

In those cases exact_form is the trivial grid integer, so 'this record has an exact_form' says nothing about whether s(n) is exactly known. For n=29 it is a rounded rational (a truncated decimal written as a fraction), which is exact as a number but is not s(29).

This is not hypothetical. During the figure work an agent concluded 'every one of the 100 verified upper bounds carries an exact_form, therefore all 100 side values are exact algebraic numbers' and stated it to the user. The claim is false and the field's naming is why. The composite figure reads reported_upper_bound throughout, which is correct, but nothing in the records makes that the obvious choice.

Same defect class as think-d1qd (claim.assurance) and think-18mu: a field named for a strong epistemic property while carrying something weaker.

DONE WHEN: the field is renamed or documented so that its relationship to reported_upper_bound is unmissable -- it is an independently certified ceiling, not the value -- and a check flags any consumer or document that treats verified_upper_bound.exact_form as the exact value of s(n).
