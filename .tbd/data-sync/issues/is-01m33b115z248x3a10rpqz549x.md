packing/tests/test_release.py::test_the_revision_is_the_length_this_repository_abbreviates_to compares len(PUBLICATION_REVISION) (sqpack/release.py, currently '277f8b1a', 8 characters) with len(git rev-parse --short HEAD). Git sizes its automatic abbreviation from the repository's object count, so the same commit abbreviates differently in different clones: a full local clone here prints 9 characters for every commit (main's c2cc1cf6c included), and the test fails there on main and on every branch, while CI's smaller clone prints 8 and passes. Found running packing-validate --fast locally on 2026-09-21 (shard B: 1 failed, 3182 passed).

The test's stated intent is that the footer's hash matches what every other tool here prints. That is a property of how the stamp is written, not of any one clone, so either pin it (write the stamp with an explicit --short=N or core.abbrev, and test against the same N), or have the test ask git for the abbreviation of the stamped commit at the stamp's own length. As it stands, the check passes or fails depending on where it runs, and will start failing in CI once the repository grows past git's threshold.
