Phase 5. Pages already builds and deploys: .github/workflows/pages.yml, repo public, site at https://jlevy.github.io/squares/, and packing/site/ is gitignored so the page is rendered in CI rather than committed. upload-pages-artifact takes packing/site whole, so a subdirectory is a URL.

The explainer keeps its URL -- that is a requirement, not a convenience. It may be linked from elsewhere, so nothing moves site/index.html; everything new is a sibling directory beneath it. Target layout: / the explainer (1.1 MB, unchanged), /workbench/ (3.1 MB), /atlas/ (3.5 MB), /embed/n-011.svg per case. About 8 MB against a 1 GB soft limit.

Three existing constraints decide the work and all three are already enforced. Self-containment: the renderer refuses any external script, stylesheet, CSS import or non-data-URI url(), which the workbench already satisfies as one file and which is why an embed can be dropped into someone else's site. Determinism: the build renders twice and fails unless the two agree byte for byte, and both spike generators already assert byte-identical regeneration. The path filter: test_the_pages_filter_covers_every_render_input compares the workflow's paths list against RENDER_INPUTS declared in devtools/render_explainer.py, so a new generator must declare its inputs or the test names what is missing.

Build it as a job whose output the existing build job collects before uploading, so a workbench failure cannot publish a broken explainer and the existing page's checks keep gating the deploy. Add a link from the explainer to /workbench/.

Caveat: 3.1 MB is a slow first load on a phone and the workbench carries all 323 transitions whether or not a visitor opens one. The fix is a smaller default payload -- the 25-pair build already exists at 714 kB -- not an external fetch, which would break self-containment.
