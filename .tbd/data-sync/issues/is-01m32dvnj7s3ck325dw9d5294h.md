Hit for real on 2026-09-21 while landing PRs 204-209.

Merging a stacked pull request does not only merge the parent: GitHub rebases every child branch onto the new base. Trees are preserved byte for byte, but every commit gets a new SHA. check_session_gate requires a declared gate commit to be an ancestor of HEAD, and treats a complete checkout that lacks the object as a failure (shallowness being the only innocent reading). So the rebase silently invalidated two terminal session records:

  session-147 declares 'full gate: fast at e2721b68' -- orphaned when chunk4 was rebased 030d109a -> 2cd99b1b
  session-148 declares 'full gate: fast at e2530693' -- orphaned when chunk5 was rebased 2bef62ae -> f5054181

Sessions 143-146 were unaffected because those branches merged as parents, keeping their SHAs.

PRs 208 and 209 both went red on validate, suite-b and packing-required with one failing step, 'terminal sessions name the gate that certified them'. Recovered by force-pushing both branches back to their pre-rebase SHAs (trees verified identical first) and merging from there.

Two things to decide, neither done:
1. Whether the merge procedure for a stack should be written down so this is not rediscovered. gh pr merge and the plain REST merge endpoint both refuse a stacked PR outright ('must be merged using the asynchronous merge REST API'), so PUT /repos/{owner}/{repo}/pulls/{n}/merge-async is the only path, and its default merge_action rebases children.
2. Whether check_session_gate should distinguish 'orphaned by a known rebase' from 'fabricated SHA'. Its docstring already contemplates the orphaned reading but the complete-checkout branch fails anyway. Any relaxation has to keep refusing an invented commit, which is the whole point of the check.

Probably also a D- defect entry, class bookkeeping, detected_by review.
